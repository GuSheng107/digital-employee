# Trigger Cases

用于人工验证 `frontend-dev-spec` 的触发稳定性。

## 应触发

以下表达应触发 `frontend-dev-spec`：

1. “按规范帮我新增一个 `user-manage` 页面模块”
2. “这个列表页的 `api` 和 `store` 应该放哪里？”
3. “帮我搭一个前端页面目录，按当前仓库规范来”
4. “整理一下这个老页面，把散落逻辑收拢到页面模块里”
5. “这块历史前端代码怎么低风险重构？”
6. “统一一下这个页面的命名和目录结构”
7. “帮我 review 这次前端改动”
8. “看看这个 PR 的目录拆分和状态设计有没有问题”
9. “检查这次 diff 是否偏离当前仓库前端规范”
10. “给我一个标准页面模块模板，适合简单列表页”

## 不应触发

以下表达不应触发 `frontend-dev-spec`：

1. “从零做一个官网首页”
2. “帮我设计一个更好看的后台 UI”
3. “生成一个 landing page”
4. “写一份前端规范提案文档”
5. “帮我润色这篇技术方案”
6. “做一个炫酷的 React 登录页视觉稿”
7. “生成一个完整 web app”
8. “帮我写 PRD 文档”
9. “做一个网页小游戏”
10. “把这篇 README 改写成对外文档”

## 边界说明

### 应与 `web-dev` 区分

当用户重点是：

- 从零搭完整网站
- 新建 web app
- 需要整体页面设计和实现

优先由 `web-dev` 处理，而不是 `frontend-dev-spec`。

### 应与 `frontend-design` 区分

当用户重点是：

- 美化 UI
- 改视觉风格
- 做设计稿级别的前端界面

优先由 `frontend-design` 处理。

### 应与 `doc-coauthoring` 区分

当用户重点是：

- 写规范文档
- 写提案
- 写说明文档

优先由 `doc-coauthoring` 处理。
