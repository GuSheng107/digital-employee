# Review Mode

用于 review 前端改动、PR、diff 或目录重构结果。

## 适用场景

当用户表达以下意图时使用本模式：

- 帮我 review 这次前端改动
- 看看这个 PR 是否符合规范
- 检查 diff 有没有风险
- 检查目录拆分是否合理

## 核心目标

优先识别：

1. Bug
2. 行为回归
3. 规范冲突
4. 维护风险
5. 缺失测试、自检或文档同步

## 输出结构

评审模式必须优先输出以下结构：

1. Findings
2. Open Questions / Assumptions
3. 简短总结

## Findings 规则

1. 按严重程度排序
2. 每条 finding 都要说明：
   - 影响
   - 原因
   - 修改建议
3. 结论要具体到文件、代码风险或行为影响
4. 若未发现明显问题，要明确写出“未发现明显问题”

## 必查维度

1. 新增页面是否遵循标准页面模块思路
2. 新增目录和文件命名是否符合仓库规范
3. 页面私有逻辑是否被错误上移到全局
4. 公共能力是否错误滞留在单页目录
5. 是否复用了统一请求封装
6. store 是否越界
7. 是否使用了 `any` 或 `as` 逃避类型检查
8. 类型边界是否清晰，函数返回值是否按规范显式声明
9. 样式是否有污染风险，样式文件命名是否符合 `index.module.css` / `kebab-case.module.css`
10. 列表页是否考虑加载态、空态和异常态
11. 路由与状态改动是否可能引发回归

## Git / PR 协作检查

当评审对象是分支、PR 或提交组合时，还需要补充检查：

1. 分支命名是否符合 `feat/xxx`、`fix/xxx`、`refactor/xxx`、`docs/xxx`、`chore/xxx`
2. commit message 是否具备足够信息量，是否贴近 Conventional Commits
3. PR 描述是否覆盖背景、变更内容、影响范围、自检结果、风险说明
4. 是否缺失与本次改动对应的规范文档或说明更新

## 新问题与历史债区分

评审时要明确区分：

1. 新问题
   - 本次改动引入的新不规范、新风险
   - 应直接指出并优先修复

2. 历史债
   - 仓库原本就存在的结构或命名问题
   - 要说明是否被本次改动扩大

## 模板引用契约

默认不读取模板目录。

只有当用户明确问：

- “是否符合标准页面模块模板”
- “这次目录拆分是不是符合模板”

才读取：

- `templates/page-module-minimal/README.md`
- `templates/page-module-full/README.md`

读取后只用来做结构对照，不要把模板内容原样搬进 review 结果。

## 测试与说明检查

评审模式需要额外检查：

1. 是否缺少必要测试或自检
2. 是否缺少规范文档同步
3. 是否缺少边界条件处理说明
4. 如果是 PR 评审，是否缺少必要的 PR 描述字段
