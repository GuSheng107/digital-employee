# Refactor Mode

用于整理历史代码、统一目录结构、拆分页面逻辑、治理请求和状态边界。

## 适用场景

当用户表达以下意图时使用本模式：

- 整理历史页面
- 把页面改成页面模块模式
- 统一目录和命名
- 收拢散落逻辑
- 治理请求散落或 store 越界

## 问题识别维度

重构模式至少从以下维度识别问题：

1. 命名不统一
2. 目录职责混乱
3. 页面逻辑过重
4. 请求散落
5. store 滥用或越界
6. 类型缺失或边界模糊
7. 样式污染
8. 历史写法与规范目标冲突

## 输出要求

重构模式输出至少包含：

1. 当前问题
2. 优先级排序
3. 分步重构方案
4. 目标结构示例
5. 风险点
6. 是否建议拆成多次提交

## 优先级原则

优先做：

1. 低风险、高收益的目录收拢
2. 命名统一中不影响行为的调整
3. 请求与类型边界梳理

谨慎做：

1. 影响引用链的大规模移动
2. 同时修改路由、状态和目录的组合式重构
3. 把历史问题一次性全部推倒重写

## 渐进重构顺序

建议顺序如下：

1. 明确当前目录职责和使用边界
2. 先收拢页面私有能力
3. 再拆请求、类型、样式
4. 最后评估是否需要局部 store 或全局上移

## 存量兼容判断

若当前代码属于历史结构，如：

- `PageA`
- `PageB`
- `Layout`

则默认判断为存量代码，优先给出渐进式方案，而不是直接要求全量对齐目标结构。

## 模板引用契约

仅在以下情况读取模板目录：

1. 用户明确要求“改成标准页面模块”
2. 目标结构需要对齐标准模板

读取后必须输出：

1. 当前结构与目标模板的差异
2. 最适合对齐 minimal 还是 full
3. 推荐的迁移步骤，而不是一次性复制模板

## 风险说明要求

必须指出以下潜在风险：

1. 路径变更导致的引用失效
2. 请求调用链行为变化
3. store 边界变更导致的状态联动问题
4. 历史样式重命名带来的选择器回归
