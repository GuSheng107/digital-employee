# 项目总体方向实现指引

> 定位：说明项目的长期方向、核心边界和演进顺序，不写具体实现细节。
> 文档状态：accepted

## 总体目标

把 `backend-agent` 建设成面向企业场景的 Agent 核心服务：核心运行能力稳定、插件能力可替换、每次执行可解释，能够逐步承载 IM、Web 和自动化任务。产品形态可以变化，但 Runtime 的领域边界和运行事实不应随入口变化。

## 架构取向

### 核心自研，插件扩展

核心层只承担所有 Agent 都必须依赖的能力：运行循环、上下文与记忆、模型兼容、任务状态、权限策略、沙箱协调和追踪事实。Skills、MCP 连接、知识库、OCR 及行业工具作为插件建设，由不同团队独立交付和演进。

核心层提供稳定的能力合同，插件通过合同接入。插件可以被替换、禁用或升级，核心 Runtime 不应因为某个插件的实现方式而改变。

### 运行时是控制平面

Agent Runtime 负责目标、上下文、模型调用、工具执行、预算、停止条件和状态转换；它不负责具体业务数据的持久化细节，也不直接实现某个外部系统的业务规则。所有长流程能力都应围绕一次可观察、可恢复的运行建立，而不是继续堆叠在单个服务方法中。

### 数据与业务分离

data 服务拥有纯数据库访问边界，agent 服务拥有业务与执行逻辑，share 包提供跨服务共用的协议、日志、轨迹和基础工具。服务之间通过轻量中转和内部协议协作，避免设置吞并所有职责的中央网关。

### 沙箱先于高风险插件

凡是涉及进程、文件、网络或第三方凭证的插件，都应以沙箱能力为前提。没有统一隔离、停止和资源限制时，只允许受信任的低风险能力进入运行链路。沙箱不是某个工具的附属功能，而是插件体系和工具执行的基础设施。

## 演进路线

### 当前：一期最小闭环

保持单 Agent 主路径，验证模型、MCP、Skill 和运行事件可以稳定协作。LiteLLM 作为模型兼容层，具体 Provider 不进入 Runtime；工具通过显式授权进入模型上下文；调试和验收优先于产品化界面。

### 下一步：二阶段服务化基础

围绕“可持续运行”补齐会话恢复、上下文选择、最小 Memory、权限策略、插件合同、沙箱底座、服务间协议和共享追踪。每一项都应能独立验收，且不把未来的复杂能力提前塞进核心循环。

### 后续：编排与企业扩展

在二阶段基础稳定后，再增加固定流程、计划与任务、子 Agent、审批恢复、知识检索、连接器、外部工作流导入和异步任务。知识检索通过外部知识库插件接入，不在核心服务内实现具体知识库平台。复杂能力以组合方式接入，不修改一期已经稳定的 Runtime 基本闭环。

### 规模化：平台治理

最后再处理插件市场、版本治理、组织级权限、成本优化、分布式存储、异步投影和高可用部署。规模化建设应由真实负载和运维问题驱动，而不是预先堆叠基础设施。

## 团队协作原则

- 核心能力由熟悉运行时和数据一致性的人员负责，插件能力按领域拆分交付。
- 每个模块先定义职责、输入输出和失败边界，再选择实现技术。
- 共享能力只提供通用机制，不把业务判断偷偷下沉到 share。
- 参考开源项目的思想和验证经验，但保持本项目领域模型的独立性。
- 文档按模块和阶段拆分；总览文档只做方向决策，具体实现另立短文档。

## 设计判断标准

面对新需求时，依次判断：它是否是所有 Agent 必需的核心能力；是否可以作为独立插件；是否需要沙箱或权限；是否必须持久化为运行事实；是否会污染 Runtime 主路径。如果不是当前阶段的必要闭环，就保留边界和验收方向，延后实现。

## 成功标准

项目最终应做到：入口可以替换，模型可以替换，插件可以替换，数据服务边界清晰；一次 Agent 执行能够被观察、解释和恢复；新增业务能力主要通过插件和组合完成，而不是继续扩大核心服务的条件分支。
