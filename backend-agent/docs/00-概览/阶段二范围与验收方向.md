# 阶段二范围筛选与验收方向

## 定位

一期已经证明了单 Agent 的模型调用、MCP 工具、Skill 工具和基本运行轨迹。二阶段不再扩展“能调用什么工具”，而是解决它能否稳定形成可持续的服务：对话可以恢复，工具可以被约束，插件可以被隔离，服务行为可以被追踪。

本文件只做方向和优先级判断。数据表、接口字段、部署参数和具体算法分别进入对应功能实现文档，不在此展开。

## 二阶段必须完成

### 1. 对话持久化与上下文选择（最高优先级）

把一次交互明确分为会话、轮次、运行和消息等层次，并保存足以重建对话和解释运行过程的事实。服务重启后，用户可以继续原会话；上下文由独立的 Context 组件选择，而不是由业务代码直接读取全部历史。

二阶段先采用有限历史窗口和明确的上下文预算。长期 Memory 只实现最小闭环：能够保存经过确认的少量用户偏好或事实，并按当前请求相关性选择性注入；不追求复杂语义检索和自动整理。

验收方向：多轮对话可恢复；工具调用不会重复污染历史；无关记忆不进入上下文；每次注入和裁剪都有可追踪依据。

### 2. 最小治理与权限边界（最高优先级）

建立 Agent、Skill、MCP 和用户之间的最小授权关系。运行时必须能够区分只读能力与有副作用能力，并在越权、风险或凭证范围不匹配时停止执行。

二阶段只做必要的策略判断、密钥引用和审计闭环。复杂审批编排、细粒度组织权限和策略管理界面后置，但不能以“内部调用”为理由绕过治理层。

验收方向：未授权工具无法被调用；敏感凭证不进入提示词和日志；关键拒绝原因可解释；权限规则不会散落在各个插件实现中。

### 3. 插件合同与沙箱基础（最高优先级）

确立核心层与插件层的稳定边界。Runtime、记忆、编排、模型兼容和权限属于核心自研能力；MCP 连接、Skill、RAG、OCR 等属于可插拔能力。插件只能通过公开能力合同访问运行时，不得直接依赖内部数据或跨层写库。

沙箱作为插件和函数调用的共同底座，在二阶段完成最小可用的隔离、资源限制和生命周期管理。它优先保障“能安全运行和终止”，不追求一次性覆盖所有操作系统和复杂执行场景。

验收方向：插件可独立启停和替换；异常插件不会拖垮 Runtime；插件的文件、网络和进程访问受统一边界约束；工具停止后不会遗留失控进程。

### 4. 服务交互、数据边界与共享追踪（高优先级）

采用轻量中转与内部请求协议进行服务间路由，不建设承担所有业务的重型中央网关。纯数据库访问集中在 data 服务；agent 服务负责业务与运行逻辑；通用模型、日志、追踪和协议能力下沉到 share 包。

日志和轨迹应由共享能力统一产生，业务模块只表达事件和业务语义。这样既能保持服务边界清晰，也能为后续恢复、诊断和成本分析提供一致基础。

验收方向：业务层不直接跨服务写库；服务之间的调用可关联到同一运行轨迹；基础日志格式和错误语义一致；中转服务只负责路由，不吞并业务职责。

## 二阶段保留但不展开

- 外部工作流 JSON 的导入、校验和封装方向：先保证兼容和可运行，不开发拖拽式设计器。
- 多 Provider 与模型故障切换：继续以 LiteLLM 为统一入口，先保持单模型主路径稳定。
- 基础运行统计和成本观察：先服务于故障定位和预算判断，不建设完整数据平台。
- 为后续编排、子 Agent、Artifact 和更长上下文预留稳定扩展边界，但不让这些能力进入二阶段主路径。

## 明确后置

二阶段不实现完整 RAG、OCR 产品化、插件市场、可视化工作流、复杂多 Agent 协作、向量数据库、分布式队列和跨地域高可用。这些能力可以有独立的方向文档和接口预留，但不得以试验性代码侵入核心运行链路。

## 阶段完成判断

二阶段完成的标志不是“增加了多少功能”，而是：一次真实 Agent 运行具备可恢复的会话上下文、最小可证明的权限边界、可替换且受隔离的插件，以及跨服务一致的事实记录。达到这些条件后，再进入复杂编排和企业连接能力，风险最低。
