## 会话与持久化

### D-001 · Event 是会话记录的依据（2026-08-30，✅）
- 决策：运行中发生的事情都写入 Event；Session 表示一次会话；Message 只作为查询和下一次模型调用使用的消息视图。
- 背景：需要查清、重放和恢复一次运行。只保存聊天消息会丢失模型请求、工具调用等过程，导致记录和实际执行不一致。
- 来源：[会话持久化总文档](../20-模块/session/总文档.md)、[DeepSeek Harness 运行时分析](../40-参考研究/deepseek-harness-agent-runtime-reference.md)。

### D-002 · 二期会话先用 SQLite，后续再换 PostgreSQL（2026-08-30，✅）
- 决策：二期会话持久化第一版使用 SQLite，后续通过 RunStore 切换到 PostgreSQL；当前一期仍使用 JSONL trace。
- 背景：一期先验证运行闭环，直接引入 PostgreSQL 会增加部署和验证成本。二期先用 SQLite 跑通 Session、Turn、Run、Event、Message 五个对象。
- 来源：[当前状态与路线图](../00-概览/当前状态与路线图.md)、[会话持久化 Phase 1](../20-模块/session/Phase1-基础可用.md)、[TODO](../00-概览/TODO.md)。

## 模型与工具

### D-003 · 用 LiteLLM 统一调用模型（2026-08-30，✅）
- 决策：用 LiteLLM SDK 调用模型；Runtime 只调用自己的 ModelGateway，不直接调用厂商 SDK 或 LangChain。
- 背景：以后更换模型平台时不改 Runtime，同时统一普通请求、工具调用、流式输出和错误处理。
- 来源：[模型网关与配置](../20-模块/model-模型网关与配置.md)。

### D-004 · MCP 和 Skill 进入 Runtime 前先统一格式（2026-08-30，✅）
- 决策：MCP 和 Skill 各自通过 Adapter 接入，进入 Runtime 前转换成 ToolSpec/ToolResult；Runtime 不处理它们的协议细节。
- 背景：MCP 和 Skill 的接入方式不同。如果把实现直接写进 Runtime，后续增加或替换工具时会不断修改核心代码。
- 来源：[工具系统：MCP 与 Skill](../20-模块/tools-工具系统-MCP与Skill.md)、[架构总览与模块边界](../00-概览/架构总览与模块边界.md)。

### D-005 · 一期不做长期记忆和自动选工具（2026-08-30，✅）
- 决策：一期不实现长期记忆（Memory），也不自动筛选工具；每个 Agent 使用哪些工具由 AgentDefinition 明确配置。
- 背景：一期先验证最小的模型-工具闭环。把所有记忆都塞进请求会增加成本和隐私风险，自动选工具也不容易排查；这两项放到后续阶段。
- 来源：[上下文组装](../20-模块/context-上下文组装.md)、[阶段二范围与验收方向](../00-概览/阶段二范围与验收方向.md)。

## 架构

### D-006 · 核心运行能力自己维护，业务能力做成插件（2026-08-30，✅）
- 决策：Runtime、上下文与记忆、模型兼容、权限、沙箱和追踪由平台自己维护；Skills、MCP、知识库、OCR 等通过插件接入。
- 背景：核心逻辑必须稳定、可控，具体业务能力则需要由不同团队独立开发和替换。所有功能都塞进 Runtime 会让代码难以维护。
- 来源：[项目定位与总体方向](../00-概览/项目定位与总体方向.md)、[DeepSeek Harness 运行时分析](../40-参考研究/deepseek-harness-agent-runtime-reference.md)。

### D-007 · 引入数据库持久化时必须经过 RunStore（2026-08-30，✅）
- 决策：引入数据库持久化后，Runtime 保存 trace 和会话数据时只能调用 RunStore，不直接依赖 SQLite、PostgreSQL 等具体数据库；一期 JSONL Recorder 暂不受此约束。
- 背景：存储方案会随部署规模变化。把数据库访问放在 RunStore 后面，先用 SQLite 验证闭环，后续换数据库时不用改 Runtime。
- 来源：[架构总览与模块边界](../00-概览/架构总览与模块边界.md)、[会话持久化总文档](../20-模块/session/总文档.md)。

### D-008 · 知识库通过外部插件接入（2026-08-30，✅）
- 决策：只定义知识库插件接口，不在 `backend-agent` 内实现具体知识库；Agent 通过工具调用插件完成知识检索。
- 背景：不同团队可能使用不同的知识库平台。统一插件接口后可以直接接入第三方平台并随时替换，核心 Runtime 只负责调用和记录，不承担知识库的存储与检索实现。
- 来源：[项目定位与总体方向](../00-概览/项目定位与总体方向.md)、[阶段需求与范围](../20-模块/阶段需求与范围.md)。
