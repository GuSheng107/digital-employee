# Agent Runtime 实现方案

## 目标与边界

本方案落实重构设计中的 Runtime、工具面收敛和可演进边界，但一期只建设 `Single` 模式。旧版把模型适配、Prompt 拼接、记忆、工具筛选和输出处理集中在 `agent_runtime/service.py`；新项目必须按一期架构图分层，任何模块不得反向依赖 HTTP 或具体 Provider。

架构图源文件：[一期-runtime架构.drawio](图/一期-runtime架构.drawio)。

## 模块与依赖方向

| 模块 | 一期职责 | 禁止承担的职责 |
| --- | --- | --- |
| API Adapter | 鉴权后转为 `RunRequest`，向客户端转发事件 | Prompt 拼装、工具调用 |
| Agent Runtime | 驱动模型-工具循环，限制预算和状态转换 | Provider / MCP 协议细节 |
| Context Builder | 生成稳定系统前缀、Skill 指令和本轮消息 | 检索长期 Memory |
| Model Gateway | 通过 LiteLLM 调用模型，归一化流和工具调用 | 决定业务工具 |
| Tool Registry / Executor | 汇总 `ToolSpec`、执行并返回 `ToolResult` | 模型重试策略 |
| MCP / Skill Adapter | 分别连接 MCP、加载受信任本地 Skill | 直接进入 HTTP 层 |
| Run Recorder | 写 trace、调用摘要与 usage | 成为业务状态机 |

依赖方向固定为 `API -> Runtime -> Context/Model/Tool/Recorder`，Adapter 只依赖 Tool Registry。接口放在 `domain` 或 `contracts`，实现放在 `infrastructure`；后续替换 LiteLLM、数据库或 MCP SDK 时不改 Runtime。

## 推荐目录

```text
backend-agent/
  app/api/                 # HTTP/SSE Adapter
  core/contracts/          # RunRequest、Event、ToolSpec 等纯数据模型
  core/runtime/            # Runtime、ContextBuilder、循环状态机
  core/tools/              # Registry、Executor、MCP/Skill Adapter
  infrastructure/model/    # LiteLLMModelGateway
  infrastructure/store/    # 一期 JSON/SQLite RunRecorder
  fixtures/weather-mcp/    # FastMCP 天气测试服务
```

一期可用 SQLite 或 JSONL 保存开发 trace，不需要 Redis。持久化访问必须经 `RunStore` 接口；二期再接 PostgreSQL、Redis、队列或对象存储。
