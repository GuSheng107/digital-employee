# 文档编写与留存规范

> 定位：约束"怎么写、怎么让文档不腐烂"。人和 AI 都照它执行。适用 backend-agent 全部 `docs/`。
> 状态：accepted

## 1. 文档风格（总方向：简洁干练）

- 一句话能说清的，不写一段；先给结论，再给理由。
- 优先用表格 / 列表 / 最小代码示例，少用大段叙述。
- 删除问候语、铺垫和重复；每个词都承担信息。
- 一个文档只回答一个问题，回答完就停。

## 2. 分层与归属

| 内容 | 放哪 |
| --- | --- |
| 为什么这么做（决策、背景、取舍） | `docs/10-决策记录/10-决策记录.md` |
| 某模块的契约 / 边界 / 分阶段落地 | `docs/20-模块/<模块名>/` |
| 总体方向、架构边界、路线图 | `docs/00-概览/` |
| 外部项目分析（非源码） | `docs/40-参考研究/` |

## 3. 模块文档拆分：总文档 + 分阶段

- **小模块**（一期已落地、无需分期）：就一个简洁 `.md`，写清定位 / 职责边界 / 输入输出合同 / 约束与坑。
- **大模块**（需要分期落地）：一个文件夹，内含 `总文档.md`（契约 + 分期总览）+ `Phase1/2/3-*.md`（每阶段一份）。
- 不按字数拆，按"职责 / 阶段"拆；一个阶段一份文档。

## 4. 决策记录

每个决策写清三件事：**选了什么（决策）、为什么选（背景）、从哪来（来源）**。格式：

```markdown
### D-00N · 标题（日期，状态）
- 决策：一句话说清选了什么。
- 背景：当时遇到什么问题、为什么这么选（1~3 句）。
- 来源：哪份文档 / 讨论 / 提交。
```

背景说不清等于没记：决策是为了解决当时的问题，丢了背景就无法避免问题重演。确实一句话能说清的才省略背景。状态：✅ 有效 / 🔁 被取代（注明被哪条取代）。

## 5. 沉淀清单（vibe coding 留存协议）

每次 vibe-coding 会话 / 每个 PR 结束，逐条自查：

1. 产生过新的、非显然的决策吗？ → 在 [决策记录](../10-决策记录/10-决策记录.md) 记一条（决策 + 背景 + 来源）。
2. 改变过某模块的职责 / 边界吗？ → 更新对应模块 `总文档.md` + [架构总览](../00-概览/架构总览与模块边界.md)。
3. 推进了某个阶段吗？ → 更新 [当前状态与路线图](../00-概览/当前状态与路线图.md)。
4. 推翻过旧决策吗？ → 旧条目标 🔁，新增一条指向它。
5. 踩过"为什么不能这么写"的坑吗？ → 写进模块文档的"约束与坑"。
6. 改动会让后来者误解吗？ → 在 [AGENTS.md](../../AGENTS.md) 地图补一句。

核心原则：会话里的临时判断不算留存，写进仓库的文档才算。

## 6. 链接纪律

- 一律相对路径；每份文档顶部"定位"、底部"相关文档"。
- 决策和设计文档中的仓库内来源必须使用可点击的相对路径；外部来源才使用 URL，并写清来源名称。
- 引用 vendored 源码写具体文件路径，不要整目录读。
- 文档状态标签：draft / accepted / superseded。

历史文档不要求一次性迁移。新建或实质修改的文档必须补齐"定位"、"状态"和"相关文档"；迁移旧文档时按本规范逐步补全。
